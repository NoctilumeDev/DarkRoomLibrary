# 项目沿革与 Git 说明

## 1. 2026 年 5 月：想法形成

暗室藏书的项目想法形成于 2026 年 5 月。最初关注的不是“完成一个课程管理系统”，而是怎样让图书馆软件同时具备清晰的业务秩序、可解释的角色分工，以及区别于通用后台模板的阅读氛围。

“暗室”表达安静、专注和低干扰的使用环境，“藏书”强调书目、流通和阅读关系。后续的纸墨、灯火、封蜡红视觉，以及读者、馆务、采购、物流之间的业务协作，都从这一想法逐步展开。

## 2. 2026 年 7 月：以课程任务为落地契机

大二短学期期间，学校布置了图书管理相关任务。基础要求较少，教师发放的教学底座也只有普通登录、用户、公告等残缺内容，没有形成完整的图书增删改查和业务闭环。

作者认为仅完成基础要求过于简单，因此没有把课程任务当作项目创意来源，而是把它作为实现 5 月构想的时间窗口：先完成课程提交所需内容，再主动扩展角色、数据模型、页面和业务规则。

## 3. 课程提交后的持续工程化

课程提交后，项目继续推进，逐步从可演示 demo 变成可运行、可验证、可维护的完整系统：

1. 补齐借阅、归还、续借、预约、罚款和库存恢复闭环。
2. 增加书评、点赞、回复、举报、内容审核和留言附件治理。
3. 增加采购员、物流员及采购到入库的跨角色协作流程。
4. 重构权限、文件生命周期、通知补偿、操作审计和中间件降级。
5. 将前端统一到 Vue 3.5、Vue Router 4、Element Plus 和 Vite 8。
6. 将后端统一到 Java 17、Spring Boot 3.5、Jakarta API 和 MyBatis-Plus。
7. 将数据库扩展为十九张相互约束的业务表，并补充并发一致性控制。
8. 建立后端、前端、真实 API、浏览器、数据库和中间件验证链路。
9. 在不拆分微服务的前提下增加可解释荐书、隐私开关和三实例批次一致性验证，数据库扩展为二十三张业务与派生表。

## 4. 教学底座与当前工程的关系

教师发放的底座是课程早期的实现辅助，不是项目想法的来源。归档原件与当前仓库对比后，可以确认两者在技术栈、包名、数据库、角色模型和业务范围上已经是不同工程：

- 原件采用 Vue 2、Vue CLI、Element UI、Java 8、Spring Boot 2.2 和 `cn.kmbeast` 包名。
- 当前项目采用 Vue 3、Vite、Element Plus、Java 17、Spring Boot 3.5、MyBatis-Plus 和 `org.darkroomlibrary` 包名。
- 原件数据库只有 `user`、`notice` 两张表，并混有问卷、考试模板残留。
- 当前数据库共 24 张物理表，包括二十三张业务与派生表及一张邮箱配额技术控制表；系统使用 5 个角色码和 6 个固定权限身份，覆盖借阅、推荐、评论、审核、采购、物流、通知、文件与审计。
- 对比范围内没有逐字节相同的源码或配置文件；少量历史组织方式也在公开前完成独立重写。

因此，准确表述是：项目构想独立形成，课程底座提供过早期实现条件，当前公开版本的业务、数据模型、界面与工程实现已经完成独立重构。

## 5. 为什么 Git 历史从中途开始

项目早期被当作一次性 demo，没有立即初始化 Git。随着后续重构范围扩大，作者才意识到需要用版本控制记录跨层修改和验证结果。

仓库不会伪造课程阶段或重构早期的提交记录，也不会回填虚构作者、日期或分支历史。首次公开提交表示“经过审查的发布基线”，不表示此前没有开发过程。

## 6. 公开与许可证边界

当前仓库继续保留来源、依赖和素材审计记录。项目源码采用 MIT License 开源；第三方依赖和外部素材仍遵循各自的许可证或使用条款。

更具体的审计对象、技术差异和当前发布边界见根目录 `NOTICE.md`。
