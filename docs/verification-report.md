## 3. 六个固定权限身份真实全链路

系统使用 5 个角色码，固定验收身份为超级管理员、馆务协调员、普通管理员、读者、采购员和物流员。6 个身份均通过真实登录接口进入系统，完整流程记录 78 次真实 API 响应，覆盖：

- 读者查询、借阅、归还、续借、预约、收藏与互动。
- 超级管理员权限调整和跨角色数据检查。
- 管理员创建采购需求。
- 采购员认领、推进并分配物流。
- 物流员更新运输、到馆和入库。
- 采购入库后库存从 `6` 增加到 `8`，重复入库未再次增加。

## 4. 并发与一致性

三个后端实例共享同一个 MySQL 测试库，按突发量 96、128、160 分三批执行。每批包含 8 个一致性场景，三批共执行 24 次场景、1,986 次场景请求，最大场景 P95 为 461 ms。三批测试均未出现破坏业务不变量的结果。

最终打包前又按相同的三实例与三批参数完成一次独立复跑，读者池分别扩大到 24、32、40，三批请求数仍为 502、662、822，合计 1,986；本次复跑最大场景 P95 为 415 ms。公开基线保留 461 ms 作为两轮中更高、也更保守的观测值。

重点验证包括：

- 库存为 1 时并发借阅只允许一个请求成功。
- 重复归还、重复预约取消和重复采购入库保持幂等。
- 用户资料、角色和业务状态更新不覆盖相邻事务。
- 通知任务使用原子认领、租约和重试，避免重复处理。

## 6. 数据库与中间件

- 27 条外键关系全部检查，孤儿记录为 0。
- 库存范围、活动借阅唯一性、活动预约唯一性、采购入库幂等和文件引用不变量违规均为 0。
- Redis 通过真实缓存键与 TTL 验证。
- Redis 故障恢复测试验证了待删除键会在恢复后的首次操作前重放，旧登录锁和旧验证码不会重新生效。
- RabbitMQ 故障恢复与队列消费通过。最终并发套件保留 2 条发送到虚构 `.local` 地址的可补偿通知任务，用于验证邮件失败后的租约、重试和恢复路径，不属于业务一致性违规。操作日志不是 RabbitMQ 消费结果，而是业务提交后通过独立事务写入的最佳努力审计。
- 后端日志错误、警告和标准错误输出均为 0。
- 前端运行时错误与警告均为 0。

真实 SMTP 邮件发送依赖外部邮箱授权码，不在公开源码的自动回归中保存凭据。邮件失败重试与补偿逻辑已由自动测试覆盖，部署者仍应在自己的邮箱环境完成一次人工收件验收。

## 7. 结论

本次验证证明当前公开基线在本地完整依赖环境中能够完成前端、后端、数据库和中间件的真实联动，并在并发、权限、状态机、浏览器运行与数据完整性方面保持一致。三实例测试只覆盖共享 MySQL 的业务一致性，不覆盖共享文件存储；当前本地文件目录仍是单机部署边界。上述延迟数据是正确性测试中的观测值，不等同于长期生产流量、跨地域容灾或无限规模保证。详细取舍见 [`architecture-review.md`](architecture-review.md)。
