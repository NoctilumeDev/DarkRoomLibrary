## 4. 并发与一致性

三个后端实例共享同一个 MySQL 测试库，按突发量 96、128、160 分三批执行。每批包含 8 个一致性场景，三批共执行 24 次场景、1,986 次场景请求，最大场景 P95 为 461 ms。三批测试均未出现破坏业务不变量的结果。

最终打包前又按相同的三实例与三批参数完成一次独立复跑，读者池分别扩大到 24、32、40，三批请求数仍为 502、662、822，合计 1,986；本次复跑最大场景 P95 为 415 ms。公开基线保留 461 ms 作为两轮中更高、也更保守的观测值。

重点验证包括：

- 库存为 1 时并发借阅只允许一个请求成功。
- 12 路并发注册共享同一规范化邮箱时恰好 3 个成功；资料换绑和物理删除同步移动或释放名额。
- 独立的三实例邮箱配额回归同时提交 100 个请求，结果为 3 个成功、97 个明确配额拒绝、0 个 HTTP 500 或其他失败；三个实例分别承担 34、33、33 个请求，最终复跑 P95 为 1,169 ms。
- `npm run test:e2e:registration-email` 通过真实注册、登录、资料换绑和物理删除接口验证：未证明邮箱控制权前只返回通用验证码错误，不泄露账号、署名或邮箱配额状态；验证后才返回精确冲突或配额结果，删除后名额可再次使用。
- 重复归还、重复预约取消和重复采购入库保持幂等。
- 用户资料、角色和业务状态更新不覆盖相邻事务。
- 通知任务使用原子认领、租约和重试，避免重复处理。

专项回归最初真实发现了配额行 `INSERT IGNORE` 共享锁升级导致的 MySQL 死锁。修复后改为从第一条语句直接取得排他行锁，并把该场景固化为 `npm run test:e2e:email-quota`；最终数据库中的配额控制值与规范化邮箱实际账号数均为 3，InnoDB 未再记录死锁。

### 4.1 v1.2.0 推荐闭环增量回归

推荐 E2E 使用三个后端实例共享同一 MySQL、Redis 和 RabbitMQ。先通过读者接口清空推荐派生记录，再把 8 个首次生成请求均衡发送到三个实例，最终只产生 1 个 `CONTENT` 批次，6 个返回条目及 `generatedAt` 完全一致。随后临时创建两名真实读者和一本候选图书，以共同收藏形成协同信号，三个实例都返回一致的 `HYBRID` 结果；临时数据在断言后完整清理。

- 三个收藏信号满足个性化阈值，已收藏图书不会出现在候选中，前三项作者保持多样。
- 关闭个性化后返回 `PUBLIC`，重新开启后恢复 `CONTENT`；共享收藏不足时不会伪造协同理由。
- 曝光、点击、推荐后收藏和“不感兴趣”四种归因均真实写入 MySQL；`INSERT IGNORE` 与唯一键保证重复事件原生幂等，不依赖异常控制流。
- “不感兴趣”后图书立即平滑移出前端列表，并在后续 30 天新批次中被过滤；收藏后来源版本变化，原条目同样立即从推荐中移除。
- Redis 可用时以全局/用户两级版本令牌避免每次聚合全部图书与行为；Redis 关闭或临时不可用时回退到 MySQL 聚合指纹，业务正确性不依赖缓存。
- 清除历史后批次、条目和事件为 0，收藏仍存在；测试结束后演示读者恢复原有 3 个收藏。
- 首轮真实测试发现新批次首次响应保留 JVM 纳秒、复用响应按 MySQL 秒精度返回的问题；实现统一为数据库秒精度后，在全新卷上复测通过。

## 7. 结论

本次验证证明当前公开基线在本地完整依赖环境中能够完成前端、后端、数据库和中间件的真实联动，并在并发、权限、状态机、浏览器运行与数据完整性方面保持一致。三实例测试只覆盖共享 MySQL 的业务一致性，不覆盖共享文件存储；当前本地文件目录仍是单机部署边界。上述延迟数据是正确性测试中的观测值，不等同于长期生产流量、跨地域容灾或无限规模保证。详细取舍见 [`architecture-review.md`](architecture-review.md)。
